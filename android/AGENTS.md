# android

The Android client. The root [AGENTS.md](../AGENTS.md) binds here too, including its loud rule:
**ask the author before deciding anything.** This file holds what the author has decided for the
Android client, and what is still open.

**It follows the web client's design decisions, chosen by the author.** What a screen shows and how
it behaves is decided once, in [web/AGENTS.md](../web/AGENTS.md), and both clients build it. Only
what is Android's own is decided here.

**It is loose for now, like the web client, by the author's choice.** Kotlin in one package, one file
per screen, settled after the first slice works. ktlint, Android lint and clippy are the only fixed
rules. **A call's code is one file, `Call.kt`, chosen by the author:** the call screen and
everything it drives, capture, codecs, playback and their threads, as `Engine.kt` holds the engine,
since a call's media lives and dies with its screen. **`ffi/` is not loose:** it follows core's strict Rust rules in [core/AGENTS.md](../core/AGENTS.md).

**Nothing moves in from `/p/test/android`, chosen by the author.** It starts clean here. Its MoQ call
code is looked at again when calls are built.

## What has been decided

| Part | Decision |
|------|----------|
| Stack | **Kotlin and Jetpack Compose**, chosen by the author: state in, screen out, as the web's React, and right-to-left for Persian built in |
| Oldest Android | **Android 10, API 29**, chosen by the author for calls: Android's MediaCodec encodes Opus only from there, so no codec library is bundled. It was Android 8, API 26 |
| Package id | **`io.github.pouriya.keryx`**, chosen by the author: tied to the repository, so it cannot clash. It can never change once installed |
| Binding | **Hand-written JNI, chosen by the author**, in `ffi/`, a workspace crate beside `web/wasm/` holding only the glue around `keryx-core`'s `client.rs` and, for calls, `keryx-moq`'s MoQ client. No UniFFI or other generator. It uses the `jni` crate's safe wrappers, not raw `jni-sys` |
| What crosses JNI | **JSON text, chosen by the author.** One `Client` with `step(input, now)`, as on the web: the input goes in as JSON text and the outputs come back as JSON text, in core's own serde shapes, the same the web sees. Kotlin keeps its own data classes for them, read with kotlinx.serialization, and they are kept in step with core by hand |
| Call keys | **`ffi/` catches the call's key in Rust, chosen by the author.** Its `step()` takes core's `JoinCall` and rekey outputs, which hold the SFrame base secret and the Bearer token, and hands them straight to `keryx-moq`, kept beside the `Client`. Kotlin gets only `{chat, call_seq}`, to start capture and show the call. A JVM string cannot be zeroed and the GC may copy it, so keys never cross JNI. Core stays as it is |
| Media across JNI | **Raw bytes for media, JSON for the rest, chosen by the author.** Kotlin calls `audio(ts, ByteArray)` and `video(ts, ByteArray, keyframe)`, and its receive thread gets device, timestamp, kind and bytes from a blocking `next()`. State, text, call events and `Closed` stay JSON in core's shapes. At about 50 audio and 15 video frames a second each way, base64 and a JSON parse per frame would cost a third more bytes and CPU on every phone |
| Call connect | **On the call's own thread, chosen by the author.** `step()` keeps `JoinCall`'s path, token, key and indexes in Rust and hands Kotlin only `{chat, call_seq}`. Kotlin's call thread then calls `Core.callConnect(handle, server)`, which blocks there for up to 10 seconds, so the chat's WebSocket on the engine thread never waits on a call. `CallKey` and `CallText` never reach Kotlin: the ffi hands them to the joined call. A `LeaveCall` drops the call on a thread of its own, since a clean close may wait, and still reaches Kotlin so capture stops |
| Call frames across JNI | **One `ByteArray` per frame, chosen by the author.** `Core.callNext(handle, timeout)` returns null on a timeout, or byte 0 as the kind: 0 audio and 1 video, then the sender's 16-byte device id, its 8-byte big-endian timestamp and the codec bytes; 2 state, 3 call event and 4 closed, then core's JSON: `{device, state}`, the call event as it came on `events`, which Kotlin feeds back into `step()` as `call_event`, and `{code, reason}`. One allocation per frame and about 20 lines of Kotlin to read it |
| Live audio | **Opus, mono, 48 kHz, 24 kbps, 20 ms frames, chosen by the author**, the same as recordings, through MediaCodec's encoder from API 29. Each frame is its own MoQ group, so a late one is just dropped. Capture is `AudioRecord` with `VOICE_COMMUNICATION` and the platform's echo canceller and noise suppressor, and playback is `AudioTrack` in communication mode. Fixed in the client for now, like the phone test's video |
| Camera | **Camera2, drawing straight into MediaCodec's `createInputSurface()`, chosen by the author**, with a second Surface for the local preview. No copies or YUV conversion in Kotlin and exact control of size and frame rate, so the lowest CPU on low-end phones, for about 150 lines of setup. CameraX would need a custom SurfaceProvider, close to Camera2 anyway, or frames copied and converted by hand |
| Call in the background | **No foreground service in the test build, chosen by the author:** the screen is kept on during a call instead, since the clients are for testing only until the redesign. Since Android 14 the microphone and camera stop in the background without one, so leaving the app mid-call mutes it. The service, of type microphone and camera with an ongoing notification and a hang-up action, comes with the redesign |
| Ring | **A card on the bare screen with Answer and Decline, and no ringtone or vibration, chosen by the author** for the test build: who calls, and video or voice from the call's body. It goes away on a join from another device, an end or a decline. No notification, since the app does nothing while closed |
| Playback | **A small audio buffer, and video on arrival with no lip sync, chosen by the author** for the test build. Audio goes through a jitter buffer that starts at 60 ms and grows to at most 200 ms when gaps appear, then `AudioTrack`, since voice crackles on a real network without one. Video is decoded by MediaCodec into a `SurfaceView` as each frame arrives, never held back for audio, so lip sync can be off by up to 0.2 s. Holding video behind the same sender's audio by their sealed timestamps comes with the redesign |
| Audio route | **Always the speaker in the test build, chosen by the author**, with no speaker button and no headset routing. Speaker for video and the earpiece for voice, moving to a wired or Bluetooth headset, with a speaker button, comes with the redesign |
| Permissions | **Asked when first needed, chosen by the author:** `RECORD_AUDIO` at the first call started or answered, and `CAMERA` when video is on or turned on. A refused one keeps that sense off, and the person still watches, listens and types, which a call allows anyway, with the `state` track saying so. This is Android's own guidance |
| Call test | **Two phones, chosen by the author:** the same APK on a second phone, logged in as a second account, in a direct chat. Two real cameras, microphones and networks |
| Call screen | **Test-bare, chosen by the author, since the clients are for testing only until the redesign:** a Video call and a Voice call button beside Send, chosen by the author, starting with the camera on or off, so both ring texts and both starting states are tested, the ring card, the other person's video full screen with the local preview in a corner, mute, video on or off, which tests the `state` track, a text field with the call's text below it, and hang up. No name, no time in the call, no camera switch and no speaker button. Material 3 only |
| File chunks across JNI | **Raw `ByteArray`s, like call media, chosen by the author.** Core's chunk bytes are `serde_bytes`, which in JSON is a list of numbers: a 1 MiB chunk would be about 4 MB of text, built and parsed on both sides. So the ffi keeps a `put_chunk`'s or `write_chunk`'s bytes in Rust, and its JSON carries only `chunk`, a number Kotlin passes to `Core.chunk(handle, chunk)` to take them. `chunk_read` and `fetched` go in through `Core.stepBytes(handle, input, bytes, now)`, with their JSON holding everything but the bytes |
| File keys | **Kept in Rust, chosen by the author, by the rule for call keys.** The ffi takes `key` out of each file of a shown `message` or `edited`, keeps it by file id, and puts it back into `download` and `edit` commands. Kotlin never sees a file's key. One key opens only its own file, whose opened bytes still reach Kotlin, so this protects files not yet downloaded |
| Sending files | **One File button beside Send, chosen by the author for the test build.** It opens the system picker with several allowed, and the text field becomes the caption. One file's kind comes from its MIME type: `image/*` image, `video/*` video, PDF and office documents doc, and anything else file. **An MP3 is music, chosen by the author:** a type of `audio/mpeg`, `audio/mp3` or `audio/mpeg3`, or a name ending in `.mp3`, whatever else the picker said, and it always goes as `audio/mpeg`. Its title, artist and duration come from `MediaMetadataRetriever`, and its embedded cover is decoded small for the BlurHash, and the file row shows them. Several images and videos go as one `media_bundle`, at most 20. The BlurHash's small pixels come from `ImageDecoder` for an image and `MediaMetadataRetriever` for a video. No voice recording yet |
| Opening files | **A row per file with Open, chosen by the author for the test build:** its name, size and kind, and the BlurHash for an image or video. Tapping downloads it into the app's cache, counting chunks, then hands it to another app with `ACTION_VIEW` through a `FileProvider`. Nothing is written to shared storage |
| Threads | **One background thread holds core's `Client`, the WebSocket and the timer**, like the web's worker. Sockets and timers stay on the platform side, as the root AGENTS.md says |
| Lifetime | **The connection lives while the app is open, for now, chosen by the author.** When the app is closed nothing runs yet. Checking for messages while it is closed is open below |
| Rotation | **The activity is kept through rotation, chosen by the author:** `android:configChanges` covers orientation, screen size and layout, and the keyboard, so Compose only lays the screen out again and the engine and a call carry on. **`onDestroy` closes the call and the engine**, so an activity that really goes leaves nothing running. In the two-phone test, turning a phone recreated the activity, which built a second engine and call beside the first: the old call kept playing unseen, and the two engines took the device's chat socket from each other several times a second. A call's video rotation is still read once at join, so turning the phone mid-call does not update it yet. Other changes, such as dark mode or the language, still recreate the activity, which is now clean but ends a call |
| Network | **OkHttp** for the WebSocket and REST, chosen by the author |
| Session | **A Bearer token, chosen by the author.** The app logs in with `/api/v1/login/token`, as root AGENTS.md says non-browser clients do. Core hands the token out once with `Token`, and takes it back in `Loaded`, so a closed app comes back logged in. It is kept with the snapshot and never logged |
| Device state | **Two snapshot slots in the app's private files, encrypted with an AES key in the Android Keystore, chosen by the author.** The key never leaves the phone's secure hardware, so a copied backup or a file dump cannot be read. The web cannot do this, which the root AGENTS.md lists as a cost. The token is kept the same way. **Everything is kept apart by server address and username, chosen by the author**, so one phone can hold accounts on several servers: the snapshot, the token and the archive. The one left behind is kept |
| Archive | **Every message and call row as the server sent it, in its own SQLite file in the app's private files, one per server address and username, chosen by the author**, opened with Android's built-in `android.database.sqlite`, with no library. Core hands each `sync` page to save; the engine writes it in one transaction and confirms, and only then does core ask for the next. Rows stay ciphertext, opened when shown, so the file needs no encryption of its own |
| Server | **The first screen asks for the server's address, chosen by the author**, such as `https://chat.example.com`, checks it with `GET /api/v1/public/features`, and remembers it. The web never asks, since the server serves it. While developing, the phone reaches this machine's `keryx serve` through `adb reverse tcp:7778 tcp:7778`, at `http://127.0.0.1:7778`. **Port 7778, chosen by the author**, since borhan holds 7777 on this machine |
| Build | **`android/Makefile`, wrapping a committed Gradle wrapper and `cargo-ndk`, chosen by the author.** `ffi/` is built for `arm64-v8a`, almost every phone in use, and `x86_64`, so it also runs in an emulator. Everything goes through `make`, as elsewhere |
| Toolchain | **What the moq experiment in `/p/test/android` already built with on this machine, as the author pointed to:** Gradle 8.9 from its cache, the Android Gradle plugin 8.7.3, Kotlin 2.0.21 and Android 15 (API 35). The NDK is r30. `dl.google.com` refuses this network, so Google's Maven and the SDK come through `redirector.gvt1.com`, as the experiment found. **That cache is gone, so the toolchain was installed again by hand:** `platform-35_r02`, `build-tools_r35`, `platform-tools_r37.0.2` and `android-ndk-r30` unzipped from `redirector.gvt1.com/edgedl/android/repository/` into `/p/Android/Sdk` as `platforms/android-35`, `build-tools/35.0.0`, `platform-tools` and `ndk/30.0.16248370`, with `~/Android` linked to `/p/Android` for room on disk, Gradle 8.9's zip placed in the wrapper's cache, and `cargo-ndk` 4.1.2 with the `aarch64-linux-android` and `x86_64-linux-android` targets |
| Look | **Simple for now, chosen by the author:** Material 3's own components and colours, with nothing of the web's look copied. The Android client first has to be good enough to test text, files and calls, and a full redesign comes after that. What screens show and how they behave still follow [web/AGENTS.md](../web/AGENTS.md) |
| Server screen | **When the screens are built, its own first screen, chosen by the author:** only the address, checked with `GET /api/v1/public/features` and remembered. The log-in screen shows the server with a Change link back to it |
| Setup link | **Pasted, chosen by the author.** The server screen offers "I have a setup link": the app takes the server and the token from `https://server/setup#token`. Nothing has to be hosted for it, and it works over plain HTTP. Opening such a link straight into the app is not built |
| Texts | **Android string resources, chosen by the author:** `values/` for English and `values-fa/` for Persian, with Android's plurals, and lint catches one missing. They are copied from the web's `en.json` and `fa.json` by hand |
| Navigation | **Our own state switch, chosen by the author:** one value says which screen shows, and the system back button pops it. No library, as the web has its own router |
| Icon | The approved logo from `web/public/favicon.svg` as an adaptive icon: ink on white, as the web's home-screen icons keep their white background |
| `make check` | **ktlint, Android lint with warnings as errors, and clippy with `-D warnings` and `cargo fmt --check` on `ffi/` and `../moq/`**, chosen by the author |
| Testing | **On the author's own phone over adb, chosen by the author.** Taps and typing through adb, the screen read through uiautomator's layout dump, and screenshots. No test framework for now |
| Order | **Files and calls first, chosen by the author.** The bare screen that logs in and sends an encrypted message works on the author's phone, checked against the web client. It stays bare and grows only what testing text, files and calls needs: no standard screens until then. A full redesign comes after, and the account screens, the chat list, the chat screen, directory search and the device list follow [web/AGENTS.md](../web/AGENTS.md) then |

## Testing

## Open: do not decide these, ask

- **Checking for messages while the app is closed.** The author wants something like a check every
  5 minutes, or another way that uses less battery than a connection kept open. Android's own
  scheduler, WorkManager, runs periodic work at most every 15 minutes, not 5. The usual low-battery
  way is a push service that wakes the app: Google's FCM, which tells Google when a message arrives,
  or a self-hosted one such as UnifiedPush
- **Plain HTTP and backups, done for now and not decided.** The app allows plain HTTP, so it can
  reach a server without TLS such as the one on this machine, and turns Android's backups off, since
  the locked files could not be opened anywhere else anyway. Whether a release keeps plain HTTP is
  to ask
- The folder layout and code style, once the first slice works
- Release signing, the store, and how the app reaches people
